## 0. 한 줄 요약

`scenario00` 송금 흐름의 **승인(approval) 단계가 PIN(assertion)을 검증하지 않음**. 틀린 PIN(`000000`)으로도 `approvalId`가 발급되고(`authMaterialValid:false`), 그 승인으로 송금이 `DONE` 된다. 서버도 이를 `predicateCode: SCN00.F28.TXN_AUTH_NOT_VERIFIED` 로 취약점 인정. proofCode = `EQP1-S00F-28-4K7M-Q2X9` (단, LMS 채점 거부 이슈는 §8 참조).

## 1. 정적 분석(Static) — "지도"를 그린 단계

정적으로 쓴 재료는 **두 가지**다.

### 1-1. Burp 캡처 XML (가장 확실한 근거)
`송금페이로드`, `송금페이로드2` (Burp items export, base64 request/response)를 디코딩.
→ 여기서 **실제로 호출된 엔드포인트와 요청/응답 바디**를 그대로 확보. 이건 추측이 아니라 사실.

디코딩으로 확정한 운영(production) 흐름:
```
POST /api/v1/recipients/resolve
POST /api/v1/transfer-previews
POST /api/v1/auth/approval-challenges   → challengeId, nonce, payloadHash, allowedMethods
POST /api/v1/auth/approvals             → approvalId  (PIN 평문 assertion)
POST /api/v1/transfers                  → status:DONE
```
그리고 `송금페이로드2`에서 **scenario00 전용 흐름**의 존재를 발견:
```
POST /api/v1/scenario00/transfer-steps/{draftId}/amount
POST /api/v1/scenario00/transfer-steps/{draftId}/confirm   ← proofCode가 응답에 등장
GET  /api/v1/scenario00/items                              ← F28~F40 문제 목록
GET  /api/v1/scenario/completions/pending
```

### 1-2. React Native(Hermes) 번들 그렙
앱은 RN이고 로직은 `assets/index.android.bundle` (Hermes **바이트코드**).
→ 소스가 아니라 **문자열만** 추출 가능. `strings` + `grep` 수준.

```bash
grep -o -a -E '/api/v1/[a-z0-9/_-]+' index.android.bundle | sort -u
grep -o -a -E 'scenario00/[a-z0-9-]+'  index.android.bundle | sort -u
grep -o -a -E '[A-Z_]{6,}(INVALID|EXPIRED|LOCKED|...)' index.android.bundle | sort -u   # 서버 에러코드
```

이걸로 **얻은 것 / 못 얻은 것**이 분명하다.

| 정적으로 얻은 것 | 정적으로 **못** 얻은 것 |
|---|---|
| 엔드포인트 **이름** 후보 (`scenario00/auth/approvals`, `/transfers` 등) | 정확한 **철자/복수형**, HTTP 메서드 |
| 서버 **에러코드 목록** (`TRANSACTION_PIN_INVALID`, `APPROVAL_METHOD_NOT_ALLOWED`, `BIOMETRIC_SIGNATURE_INVALID` …) | 요청 **바디 필드 구성**, 필수 헤더(`Idempotency-Key`) |
| 채점 관련 경로 단서 (`/scenario/completion`, `monitor/claim`, `proofBox`) | **인증 검증 로직** (서버에만 존재 → 애초에 클라에 없음) |
| 두 벌의 API 네임스페이스(`/api/v1/...` vs `/api/v1/scenario00/...`) 존재 | 어느 쪽에 취약점이 심겼는지 |

> ⚠️ Hermes 바이트코드라 문자열이 **다닥다닥 붙어서**(`transfer-previewscreen-...`) 나와 철자/경계 판별이 불안정했다. 그래서 `transfer-priviews` 같은 오타/오판이 났고, **동적 확인으로만** 바로잡혔다.

## 2. 동적 분석(Dynamic) — 실제로 뚫은 단계

**핵심: 이 문제는 정적만으로 절대 못 푼다.** 취약점(승인 단계가 PIN을 검증 안 함)은 **서버 측 로직**이고 클라 번들에 존재하지 않는다. 오직 **Repeater로 요청을 하나씩 변조해 응답을 관찰**해야 드러난다.

동적으로 확인한 사실들(전부 Repeater 실측):

1. **운영 승인은 안전하다** — `POST /api/v1/auth/approvals`에 틀린 PIN → `401 TRANSACTION_PIN_INVALID`.
2. **method 혼동 차단** — `method:"BIOMETRIC"`로 바꿔치기 → `400 APPROVAL_METHOD_NOT_ALLOWED` (allowedMethods 서버 강제).
3. **생체 등록은 PoP 기반** — `enrollment-challenges`(+PIN) → `proofPayload` → 개인키 서명 → `credentials`. 하드웨어 attestation 없음. (이 경로는 결국 F28과 무관했음.)
4. **scenario00 승인은 취약하다 (= 정답)** — `POST /api/v1/scenario00/auth/approvals` 에 `assertion:"000000"`(틀린 PIN) → **`200` + approvalId 발급, `authMaterialValid:false`**.
5. **그 approvalId로 송금 완료** — `POST /api/v1/scenario00/transfers` (바디 `approvalId`만 + `Idempotency-Key` 헤더 필수) → `200 DONE, authMaterialValid:false`.
6. **채점 기록 확인** — `GET /api/v1/scenario00/completions` (바디 `{"transferId":"..."}`) → `predicateCode: SCN00.F28.TXN_AUTH_NOT_VERIFIED`, `proofCode: EQP1-S00F-28-4K7M-Q2X9`.

동적 과정에서 바로잡은 오판들(= 정적의 한계):
- `transfer-steps/confirm`의 proofCode가 **고정 데코이**임을 발견(틀린 PIN·맞는 PIN·금액 무관하게 항상 동일, `completions/pending`은 계속 빈 배열).
- `/scenario/completion` POST는 **404**, 실제 기록 조회는 `/scenario00/completions` (복수형, 바디에 transferId).
- `scenario00/transfers`는 바디에 `previewId` 넣으면 **500**, `approvalId`만 + 헤더라야 통과.

## 3. 취약점 상세 (F28 / 거래 인증수단 검증)

- **유형:** 인증(Authentication) 검증 결과 미강제 — 승인 토큰을 인증 성공 여부와 무관하게 발급.
- **근본 원인:** `scenario00/auth/approvals`가 `assertion`(PIN) 불일치(`authMaterialValid:false`)를 **판정만 하고 승인 발급을 차단하지 않음**. 인증과 인가(승인 발급)가 분리되어 실패가 게이트로 작동하지 않는다.
- **영향:** 올바른 간편비밀번호를 몰라도 임의 송금 완료 가능 — 2차 인증 완전 우회.
- **서버 판정:** `predicateCode: SCN00.F28.TXN_AUTH_NOT_VERIFIED`.
- **대응:** 승인 발급 전 `authMaterialValid == true` 강제. false면 `401`로 거래 중단(approvalId 미발급, 잔액 차감/송금 레코드 생성 금지).

## 5. 정적 vs 동적 — 정직한 판단

**질문: 소스코드로만 판단했나, 아니면 동적으로 API 하나하나 찾아낼 정도였나?**

답: **혼합(hybrid)이며, 결정적 부분은 전적으로 동적이다.**

- **정적(번들 리버싱)의 역할 = 지도 제공.** "이런 엔드포인트가 있다/두 네임스페이스가 있다/이런 에러코드가 있다"까지. 하지만 Hermes 바이트코드라 **로직은 못 읽고 문자열만** 봤다. 철자·메서드·바디·필수헤더는 불확실했다.
- **동적(Repeater)의 역할 = 발견과 증명.** 취약점 자체(승인이 PIN을 검증 안 함)는 **서버에만 있는 로직**이라 클라 소스엔 아예 없다. 틀린 PIN을 넣고 `approvalId`가 나오는지 **직접 쏴봐야만** 드러난다.
- 실제로 정적이 준 후보 중 상당수는 동적에서 **404/400/500/오타**로 교정됐다. 즉 **정적 단독으로는 못 풀었고**, 동적 단독으로도(엔드포인트 지도가 없으면) 비효율적이었을 것. **둘의 결합**이 정답.

한 줄로: **"번들로 문을 찾고, Repeater로 문을 열었다."** 서버 사이드 비즈니스 로직 결함은 본질적으로 동적 테스트의 영역이다.

## 7. API 경로를 "동적으로" 찾는 법 (정석)

소스가 없거나 난독화돼도 이게 **본류**다.

1. **프록시 세팅:** Burp + 안드로이드 에뮬레이터/기기. 앱 트래픽을 전부 Burp로.
2. **SSL 피닝 우회:** 이 앱엔 F37(SSL 피닝) 항목이 있으므로 피닝이 있을 수 있음 → Frida `objection` / `frida-script`로 unpinning 후 HTTPS 평문 관찰.
3. **정상 플로우 전수 수집:** 송금을 **정상적으로 끝까지** 한 번 수행 → Proxy history에 모든 단계 기록(previews→challenge→approval→transfer). 이게 공격의 베이스라인.
4. **엔드포인트 맵 작성:** history에서 호스트/경로/메서드/바디를 표로 정리. 여기서 `scenario00` 네임스페이스와 `completions` 같은 채점 경로를 자연히 발견.
5. **Repeater 변조 루프 (핵심):** 각 단계 요청을 Repeater로 보내며 한 번에 하나씩 변조:
   - 인증값(assertion)을 **틀린 값/빈 값/타입 변경**으로 → 응답 코드와 `authMaterialValid` 관찰.
   - method/파라미터 바꿔치기, 단계 생략, approvalId 재사용 등.
   - **응답의 상태 전이**(200 vs 401 vs 400)와 **의미 필드**(`authMaterialValid`, `integrityMatch`, `processedCount`, `proofCode`)를 오라클로 사용.
6. **채점 오라클 활용:** `GET /scenario00/items`(solvedAt), `GET /scenario00/completions`(predicateCode/proofCode)로 "서버가 취약으로 인정했는지" 확인.

> 이번 케이스에서 결정타는 5번이었다: **운영 `auth/approvals`(401) vs scenario00 `auth/approvals`(200+발급)** 의 차이를 Repeater로 직접 비교한 순간 F28이 드러났다.

## 8. 미해결 이슈 — proofCode LMS 채점 거부

- 서버 공식값 `EQP1-S00F-28-4K7M-Q2X9` 를 LMS 단답에 제출 → **하이픈 유/무 모두 오답**.
- `solvedAt`이 **2026-11-05 15:27:26** 에 고정(최초 1회 풀이만 기록, 리셋 API 없음) → 재시도해도 같은 값.
- enrollment(`EQED-FQF7…`)는 "실습자 인증 코드"와 일치 확인.
- 남은 가능성:
  1. **제출 시 문자 혼동** (`0↔O`, `1↔l/I`) → Burp 응답에서 **복사-붙여넣기**로 재제출 권장.
  2. **앱↔LMS 동기화/채점 레이어 문제** → 요청 변조 범위 밖. `/scenario00/completions` 기록 + `items`의 `F28:SOLVED`를 증거로 **운영/강사 문의**, 또는 LMS `정답자 게시판` 확인.
- **기술적 공격은 완결됨** (서버가 `TXN_AUTH_NOT_VERIFIED`로 인정). 미해결은 채점 레이어 한정.

## 11. 순수 동적(Dynamic-only) 루트 — 리버싱 없이 푸는 법

**결론 먼저: 동적만으로 풀 수 있다. 오히려 이게 정석이다.** 취약점(승인 단계가 PIN을 검증 안 함)은 **서버 측 로직**이라 클라 번들에 답이 없다. 정적은 "지도"만 주고 "정답"은 못 준다. 정적 단독으로는 **불가능**, 동적 단독으로는 **가능**.

### 11-1. 순수 동적 절차

1. **프록시 + 피닝 우회 (유일한 전제)**
   Burp 연결. 이 앱엔 F37(SSL 피닝)이 있으니 Frida/`objection`으로 unpinning 후 HTTPS 평문 관찰.
   → 런타임 후킹이지 "소스 리버싱"이 아니다.

2. **앱 정상 사용 → 엔드포인트 자동 수집**
   송금을 정상으로 끝까지 1회 수행. Proxy history에 두 네임스페이스가 그대로 찍힌다:
   - 운영: `/api/v1/auth/approvals`, `/api/v1/transfers`
   - 시나리오: `/api/v1/scenario00/transfer-steps/...`, `/api/v1/scenario00/items`

3. **패턴 추론으로 숨은 미러 엔드포인트 도달 (핵심, 정적 불필요)**
   "운영에 `/auth/approvals`가 있고 시나리오는 `/scenario00/` 프리픽스" → 그대로 **`/api/v1/scenario00/auth/approvals`를 Repeater로 쏴본다**. 200이면 존재 확정.
   같은 방식으로 `/scenario00/transfers`, `/scenario00/completions` 도달.
   퍼징 워드리스트도 간단: **운영 경로들의 prefix만 `scenario00/`로 치환**.

4. **Repeater 변조 루프 → 취약점 발견 (100% 동적)**
   운영 `auth/approvals`(틀린 PIN → 401) vs scenario00 `auth/approvals`(틀린 PIN → **200 + approvalId, authMaterialValid:false**). 이 **차이를 직접 비교**하는 순간 F28 확정.

5. **채점 오라클로 검증**
   `GET /scenario00/items`(solvedAt) · `GET /scenario00/completions`(predicateCode/proofCode).

### 11-2. 정적이 실제로 기여한 것 (없어도 됐던 것)

| 정적이 준 것 | 동적만으로 대체 |
|---|---|
| 엔드포인트 이름 사전 | ✅ 패턴 추론 + 경로 퍼징 |
| 서버 에러코드 목록 | ✅ 변조하다 응답으로 다 나옴 |
| 두 네임스페이스 존재 | ✅ Proxy history에 그대로 보임 |
| **취약점 로직** | — 정적은 애초에 못 줌(서버에 있음) |

### 11-3. 동적에서 유일하게 번거로운 지점

숨은 미러 엔드포인트(`scenario00/auth/approvals`)는 **정상 앱 UI에서는 호출되지 않을 수 있다**(앱의 F28 실습은 `transfer-steps/confirm`만 씀). 그래서 **패턴 추론/경로 퍼징**이 필요하다. 번들 그렙은 이 이름을 공짜로 알려줘 **추측 횟수를 줄여준 것**뿐, 필수는 아니다.

### 11-4. 한 줄 정리

- **동적 단독: 가능** — 서버 비즈니스 로직 결함의 정석 접근.
- **정적 단독: 불가능** — Hermes라 로직도 안 읽히고, 핵심이 서버에 있음.
- 정적의 값어치 = "추측 공간을 좁혀 속도를 높인 보조재". **"번들로 문을 찾고, Repeater로 문을 열었다"** 는 편의였을 뿐, 문은 Repeater만으로도 찾을 수 있었다.
